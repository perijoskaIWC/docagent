DocAgent: from an export to a solution design

We build one realistic AI application on the Microsoft stack and use it as a lab. Upload an export from any business system, let the AI work out which system it is, and get an evidence-backed solution design. Every major step has several interchangeable implementations, and we measure which works best.

01 · Direction

What we're doing and why

The goal is learning by building

One realistic use case is our test bench. We try different agent architectures, RAG approaches and detection methods side by side on the same inputs, measure them, and learn what works on the Microsoft stack and why. The experiment notes and the pattern catalog are the lasting output, more than the app.

Generic, new and clean

A new .NET application, built from scratch. It isn't specific to any product, customer or engagement and contains no existing code, files or documents. Test exports are synthetic; knowledge comes from public sources or is written by us.

A working app

Upload → detect → design → review → ask. Deployed on Azure and traced end to end.

Measured comparisons

Seven experiments with reports: detection, agent architecture, retrieval mode, search setup, tools over MCP, model mix, memory.

Reusable knowledge

Experiment notes, an architecture document and a pattern catalog the practice can use on real projects, including what maps to TRYche.

02 · The product

What a user does

1 · Upload

Export pack

Zip or files: CSV, Excel, JSON, XML, XSD, OpenAPI, SQL, PDF.

2 · Detect

Which system?

"Helio Service, 92%, because of the API title, webhook config…" The user can correct it.

3 · Choose

Design type

Assessment, integration or migration. Plus a target, a short brief and the lab strategy.

4 · Generate

Evidence-backed design

Drafted by agents, validated by code, reviewed in a bounded loop.

5 · Use

Read, ask, compare

Download it, ask questions in a streamed chat, rerun with another strategy and compare.

Every statement in a design is one of three things

  • Evidenced: cites the exact field, entity or file location in the export, or a knowledge-base source
  • Assumption: marked as such in the document
  • Unknown: shown as [TBD] and listed as an open question. No invented fields, systems or numbers.

Design principles

  • Deterministic first: code extracts names, types, keys and locations. Agents interpret and design.
  • Agents read through drill-down tools, served over MCP, instead of whole files in a prompt.
  • Agents return structured parts. Code validates and renders them.
  • Evidence, or say so: every statement cites a source or is flagged.
  • Deterministic checks prove nothing was lost, next to the LLM reviewer.
  • Every slot is swappable and measured. A new strategy is a new keyed implementation plus an eval run.

How seven people work in parallel

  • Shared contracts in DocAgent.Core: written, compiling on .NET 10, owned by Darko
  • Fakes behind every contract, one feature flag per area, so nobody waits for anybody
  • Keyed strategies: each run picks its detector, author and retrieval mode; the UI only offers what exists
  • The skeleton first: Elena and Darko deliver it by 6 Nov; everyone else builds behind their contract from 9 Nov
